Logic an toàn

  • isTypingTarget(e.target): phím chữ (E/M) không trigger khi user đang gõ trong <input>, <textarea>, <select>, hoặc element contenteditable (như Tiptap).
  • Esc trong inline-edit chỉ hủy edit, không đóng modal — tránh user mất gõ vì lỡ tay.
  • Bỏ qua nếu có modifier (Ctrl/Meta/Alt) — tránh xung đột với shortcut hệ thống.
  • Auto-detect Mac vs Windows qua navigator.userAgent để hiển thị ⌘ hoặc Ctrl.

  • Nếu một số ảnh upload fail: issue vẫn được tạo thành công, hiển thị cảnh báo "N ảnh upload thất bại — issue đã được tạo", không emit close để user có thể xem trạng thái từng thumbnail.
  • Nếu API tạo issue fail: bắt error message từ err.data.title[0] hoặc err.data.detail, hiển thị trong banner đỏ.

12.5 Logic suy luận start/end cho issue

API không có field start_date cho issue, nên cần infer:

function inferIssueRange(issue, sprintMap) {
  start = issue.due_date  ? null : safeParse(issue.created_at)
  start = start || safeParse(sprint.start_date)
  end   = safeParse(issue.due_date) || safeParse(sprint.end_date)

  // Nếu có start + estimated_minutes nhưng không có end
  if (start && !end && issue.estimated_minutes) {
    days = ceil(estimated_minutes / (60 * 8))  // 8h workdays
    end = addDays(start, days)
  }

  // Fallback 1-day window nếu chỉ có 1 đầu
  if (!start && end) start = addDays(end, -1)
  if (start && !end) end = addDays(start, 1)
}

Issue thiếu cả start lẫn end → bị filter ra (không spam Gantt với dòng trống).

15. Fix bug thông báo khi có người comment

15.1 Triệu chứng

Khi một user comment lên issue, recipient (assignee / @mentioned) không nhận được toast hay browser notification, badge "Bell" trên top bar không tăng.

15.2 Nguyên nhân tìm thấy

  • WebSocket message handler quá strict: chỉ accept đúng data.type === 'notification'. Nếu BE gửi shape khác (vd data.event, hoặc payload lồng trong data.notification) → message bị drop âm thầm (catch rỗng nuốt lỗi).
  • Không có polling fallback: nếu WS rớt giữa chừng hoặc token hết hạn, recipient sẽ mất hoàn toàn thông báo cho đến khi reload trang.
  • Không reconnect khi token refresh: useApi refresh token sau 401 nhưng WS vẫn dùng token cũ → server kick connection.
  • Không có keep-alive ping: server có thể đóng connection sau ~60s idle.
  • Sau khi post comment, FE không trigger refresh nên người gửi không nhận feedback gì.

15.3 Các fix đã làm

FileThay đổi
stores/notifications.ts
  • Lenient message handler: accept cả data.type, data.event, payload lồng (data.notification, data.data); detect "looks like notification" qua nhiều fallback.
  • Ping mỗi 25s giữ connection alive ({type:'ping'}).
  • Polling fallback 30s: gọi fetchUnreadCount(), nếu tăng thì fetch full list để surface toast.
  • Reconnect khi token đổi: lưu lastWsToken, so sánh trước khi mở socket mới.
  • Action refreshSoon(): cho phép component gọi sau khi tạo comment / mention.
  • Log warning thay vì swallow lỗi parse.
components/IssueComments.vue Sau khi POST /api/comments/ thành công → gọi useNotificationsStore().refreshSoon() nudge để recipient thấy nhanh hơn.
layouts/default.vue Watch authStore.accessToken: token đổi → connectWebSocket(newToken) rebuild connection.

15.4 Lý do dùng polling kèm WS

WebSocket là realtime nhưng cũng dễ "lặng lẽ chết" (mạng yếu, proxy timeout, browser tab background). Polling 30s là layer phòng thủ — chi phí rất rẻ (chỉ /api/notifications/unread_count/), nhưng đảm bảo notification luôn xuất hiện trong vòng tối đa 30 giây ngay cả khi WS bị down.

Cho phép tạo issue mới bằng cách copy issue đang xem (giống ~80%, chỉ chỉnh sửa phần khác biệt) → tiết kiệm thao tác khi tạo nhiều issue giống nhau.

18.2 Flow

  1. User mở IssueModal chi tiết của issue cần copy.
  2. Trong sidebar metadata, có nút mới "Duplicate issue" (cạnh "Xóa issue").
  3. Click → CreateIssueModal được mount lồng bên trong, prefill toàn bộ field từ issue gốc.
  4. Title có prefix "Bản sao — " để dễ phân biệt.
  5. User chỉnh sửa rồi bấm Tạo Issue như flow tạo thường.
  6. Sau khi tạo xong → toast "Đã tạo bản sao XYZ-123", đóng CreateIssueModal, emit updated.

18.5 UX detail

  • Nested modal: CreateIssueModal mount bên trong IssueModal (cả hai Teleport to body) → user thấy form mới đè lên modal cũ, vẫn có animation slide-from-right.
  • Title prefix "Bản sao — " (truncated 200 ký tự) làm dấu hiệu trực quan, user có thể chỉnh lại.
  • Status default = 'todo': dù defaultStatus được truyền từ issue gốc, status mới luôn được reset về todo trong handleSubmit (Status không nằm trong prefill prop).

18.6 Tradeoffs

  • Không có BE endpoint /duplicate: Implement FE-only bằng cách dùng lại API POST /api/issues/. Đỡ phụ thuộc BE, nhưng các quan hệ phức tạp (subtasks/attachments) phải copy thủ công nếu cần.
  • Không copy attachments: nếu cần, có thể bổ sung sau bằng cách: sau khi tạo issue mới, gọi /api/attachments/duplicate?from=X&to=Y hoặc tải về rồi upload lại.
  • Permission: Duplicate cần canCreateIssue trong project. Hiện CreateIssueModal đã tự handle qua project membership.

team_score = 0.5·completion + 0.3·on_time + 0.2·quality   (cấu hình, cap 1.2)

member_bonus = pool × (SP_done × level_weight) / Σ đóng góp

11. Tradeoffs & tương lai

  • Sequential upload: an toàn cho rate limit, dễ hiển thị tiến trình từng ảnh. Có thể đổi sang Promise.all + concurrency=3 nếu user thường upload nhiều ảnh.
  • Progress giả lập: dùng setInterval tick 10%. Để chính xác hơn cần đổi fetch → XMLHttpRequest với upload.onprogress hoặc Streams API.
  • Paste ảnh từ clipboard: chưa hỗ trợ trong panel (chỉ drag-drop + click). Có thể thêm @paste handler ở element root của panel.
  • Embed ảnh trong mô tả: hiện ảnh là attachment riêng. Có thể tích hợp Tiptap Image extension để chèn inline trong description (cần thêm endpoint upload-and-return-URL).
  • Rollback khi upload ảnh fail: hiện nếu fail, issue vẫn tồn tại. Có thể thêm option "Xóa issue đã tạo" hoặc retry button cho từng ảnh.
  • Phím tắt mở rộng: hiện chỉ E/M/Esc/Ctrl+Enter. Có thể thêm S (status), P (priority), A (assignee), C (focus comment), ? (help modal) trong tương lai.
  • Mobile: sidebar 1100px sẽ tràn trên mobile. Đã dùng w-full max-w-[1100px] nên adapt được, nhưng UX hai cột scroll trên mobile chưa tối ưu — cần test thực tế.
  • Gantt — issue thiếu start_date: hiện infer từ created_at / sprint.start_date / estimated_minutes. Để chính xác hơn, BE nên bổ sung field start_date cho issue (tương tự due_date).
  • Gantt — Excel format: dùng HTML-table → .xls. Đơn giản nhưng không có công thức / chart / merge sheets. Nếu cần xuất chuẩn xlsx (mở được Google Sheets, LibreOffice), nên thêm dep exceljs hoặc xlsx (SheetJS).
  • Gantt — drag-resize bar: hiện bars là display-only. Có thể thêm drag để chỉnh start/end và PATCH lên BE — cần BE hỗ trợ start_date trước.
  • Gantt — dependencies (FS/SS/FF/SF): chưa có. Có thể vẽ arrow giữa các bar nếu BE lưu quan hệ parent/blocker.
  • Gantt — critical path: chưa tính. Cần graph dependencies trước.
  • Gantt — performance: render mọi bar trong DOM. Với project >500 issues + view tháng, có thể lag scroll. Nếu cần, áp dụng virtual scrolling (chỉ render rows trong viewport).
  • Google scope drive (full): scope nhạy cảm, có thể cần Google verification cho production. Thay thế dài hạn: Picker + drive.file nếu muốn hạn chế quyền.
  • Drive activity queryset: đã lọc theo membership; admin thấy mọi activity qua filter_by_project_membership bypass.
  • Company OAuth secrets: lưu plaintext trong DB — cân nhắc encrypt at rest cho production.
